# Beyond Handcrafted Security: Towards Self-Evolving Defense for LLM Agents

Ruan, Jiajun, Li, Peiyang, Chen, Yukun, Li, Fengting, Feng, Chao · 2026

[论文原文](https://arxiv.org/abs/2608.12977)

## 核心机制

根据失败轨迹自主演化运行时 harness 防御

## 适用范围与局限

防御构造工作，正文以 SafeEvolve 等作代表

## 详细解读

### 论文核心总结

这篇论文针对大语言模型（LLM）Agent在运行时面临的安全威胁，提出了一个名为**HARD（Harness-based Autonomous Runtime Defense Evolution）**的自演化运行时防御框架。论文的核心洞察是：现有的运行时防御机制都是人工手动设计且部署后静态不变的，无法应对不断演化的攻击模式。为解决这一问题，作者首先建立了一个以"harness"（运行时外壳/中间层）为中心的统一防御形式化框架，将运行时防御分解为**上下文构造**（context construction）和**动作解释**（action interpretation）两个可编辑的干预接口；然后在此基础上提出HARD框架，通过收集Agent执行失败的轨迹、将失败归因到对应的防御组件、并由LLM自动改进相应的防御制品，实现防御机制的自主迭代演化。实验表明，HARD在四类攻击场景下均显著优于手工设计的静态防御，同时保持了较高的正常任务完成率。

### 一、研究背景与动机

#### 1.1 LLM Agent的安全风险

LLM Agent已经从被动的文本生成器演变为能够检索外部信息、调用工具、维护状态并在外部环境中执行操作的交互式系统。这种能力使它们能够完成代码仓库级别的编程、长周期的Web工作流等复杂任务，但同时也将安全风险从孤立的文本生成转移到了**工具介导的运行时执行**——一次不安全的工具调用就可能造成严重后果（如删除文件、泄露隐私、执行恶意命令等）。

#### 1.2 现有防御的局限

防御手段主要分两个层面：

- **模型层面防御**：通过微调、偏好优化、强化学习等修改模型参数，但需要访问模型参数，且存在安全性与实用性之间的权衡。
- **运行时防御**：在Agent执行循环中引入安全机制（如过滤不安全输出、约束工具调用等），无需修改模型参数，更适合已部署的系统。  
  然而，现有运行时防御存在根本性问题：

1. **手工设计且静态不变**：部署后防御策略固定，无法应对新出现的攻击模式。
2. **失败空间开放性**：LLM Agent的失败模式本质上是开放的，无法事先穷举。
3. **自适应攻击**：攻击者可以持续修改策略来对抗已部署的防御，导致失败分布随时间变化。  
   这引出了论文的核心研究问题：**如何使运行时防御能够自主演化以适应新出现的攻击？**

### 二、LLM Agent与安全威胁模型

#### 2.1 LLM Agent形式化

论文将已部署的LLM Agent建模为 $\mathcal{A} = (M_\theta, H)$，其中：

- $M_\theta$ 是参数固定的语言模型
- $H$ 是**运行时harness**（外壳），负责中介模型与外部环境 $\mathcal{E}$ 及持久化Agent制品 $\rho$ 之间的交互  
  持久化制品 $\rho = (m, s)$，其中 $m$ 是持久记忆，$s$ 是已安装的技能/插件/工具规格。  
  Harness由两个函数组成：$H = (\phi_H, \psi_H)$
- **上下文构造函数** $\phi_H$：决定将哪些信息（来自当前任务、交互历史、持久化制品）呈现给模型
- **动作解释函数** $\psi_H$：决定如何将模型输出转换为可执行操作（包括解析、验证、转换、阻止或请求确认）  
  具体执行流程：给定用户任务 $x$，设 $\tau_t = (x, a_0, o_1, \ldots, a_{t-1}, o_t)$ 为第 $t$ 步之前的交互历史。Harness首先构造模型上下文：  

  $\displaystyle c_t = \phi_H(\tau_t, \rho)$

    
  语言模型生成输出：  

  $\displaystyle y_t \sim M_\theta(\cdot | c_t)$

    
  Harness解释输出为可执行动作：  

  $\displaystyle a_t = \psi_H(y_t, \tau_t, \rho)$

    
  执行 $a_t$ 产生下一个观察 $o_{t+1}$，并可能修改 $\rho$。

#### 2.2 四种安全威胁

论文假设攻击者无法修改模型参数 $\theta$ 或已部署的harness $H$，考虑以下四种攻击场景：

1. **直接提示注入（DPI）**：攻击者直接控制用户任务 $x = x_{\text{adv}}$，任务本身包含恶意目标或指令。
2. **间接提示注入（IPI）**：用户任务是良性的 $x = x_{\text{ben}}$，但攻击者控制Agent读取的外部内容（如网页、邮件、文档），某个观察 $o_j = o_{j,\text{adv}}$ 包含对抗性指令。
3. **记忆污染（MC）**：评估交互以良性任务和已被污染的持久记忆 $m = m_{\text{adv}}$ 开始。攻击者可能在早期会话中植入恶意规则、伪造授权、虚假事实或触发条件指令。
4. **技能投毒（SP）**：评估交互以良性任务和已被篡改的技能/插件 $s = s_{\text{adv}}$ 开始。被投毒的技能可能保留其宣传的功能，同时嵌入隐藏指令、恶意逻辑或触发器。

### 三、以Harness为中心的运行时防御

#### 3.1 运行时防御作为Harness优化

论文将运行时防御形式化为对harness的优化问题。设 $\mathcal{H}$ 为可部署的运行时防御配置空间，对于任务分布 $\mathcal{D}$，每个harness $H \in \mathcal{H}$ 诱导一个Agent-环境轨迹分布：  

$\displaystyle \tau \sim \mathbb{P}_{M_\theta, H, \mathcal{E}}(\cdot | x), \quad x \sim \mathcal{D}$

  
定义两个互补的轨迹级目标：  

$\displaystyle J_{\text{safe}}(\tau) \in [0,1], \quad J_{\text{util}}(\tau) \in [0,1]$

  
其中 $J_{\text{safe}}(\tau)$ 衡量安全性能（防止对抗行为和不安全动作的能力），$J_{\text{util}}(\tau)$ 衡量任务实用性。  
运行时防御目标形式化为：  

$\displaystyle H^\star \in \arg\max_{H \in \mathcal{H}} \mathbb{E}_{x \sim \mathcal{D}, \tau \sim \mathbb{P}_{M_\theta, H, \mathcal{E}}(\cdot|x)} [J_{\text{safe}}(\tau) + \lambda_u J_{\text{util}}(\tau)]$

  
这个公式揭示了运行时防御的本质：通过harness设计来提升Agent安全性，但不可避免地引入安全性与任务实用性之间的权衡。

#### 3.2 基于Harness的防御构造

Harness框架提供了一个结构化的运行时防御构造原则：

- **上下文侧防御**（$\phi_H$）：通过调控模型输入来提升安全性，包括标记不可信内容、过滤与任务无关的信息、检测注入指令等。
- **动作侧防御**（$\psi_H$）：通过调控Agent执行来提升安全性，包括工具调用的守卫模型、最小权限策略执行、动态合成的动作约束、执行隔离等。  
  这个形式化将现有的各种运行时防御方法统一到一个框架下：防御机制可以通过优化 $\phi_H$、$\psi_H$ 或两者同时来构造。

### 四、HARD：基于Harness的自主运行时防御演化

#### 4.1 失败驱动的防御演化

HARD的核心思想是将人工分析失败轨迹并迭代改进防御策略的过程自动化。在演化迭代 $t$，给定当前harness $H_t$，执行以下三步：  
**（1）攻击驱动的轨迹收集。** 从攻击任务分布 $\mathcal{A}$ 中采样攻击任务：  

$\displaystyle \mathcal{X}_t = \{x_i\}_{i=1}^N \sim \mathcal{A}$

  
在当前harness $H_t$ 下收集执行轨迹：  

$\displaystyle \mathcal{T}_t = \{\tau_i\}_{i=1}^N, \quad \tau_i \sim \mathbb{P}_{M_\theta, H_t, \mathcal{E}}(\cdot | x_i)$

  
**（2）失败识别。** 分析收集的轨迹，识别当前harness未能达到安全或实用性目标的失败案例：  

$\displaystyle \mathcal{F}_t = \{\tau_i \mid \tau_i \in \mathcal{T}_t, J_{\text{safe}}(\tau_i) < \delta_s \lor J_{\text{util}}(\tau_i) < \delta_u\}$

  
**（3）Harness演化。** 将失败集 $\mathcal{F}_t$ 提供给基于LLM的演化器来更新harness：  

$\displaystyle H_{t+1} = \mathcal{E}(H_t, \mathcal{F}_t)$

  
演化器在约束下生成改进的harness配置：  

$\displaystyle \min_{H'} \Delta(H_t, H') \quad \text{s.t.} \quad H' \text{ resolves the failures in } \mathcal{F}_t$

  
其中 $\Delta(H_t, H')$ 衡量对现有harness引入的变更程度。这个约束鼓励演化器只做必要的修改，在提升防御效果的同时保持现有实用性。

#### 4.2 失败轨迹路由与演化编排

不同的失败轨迹暴露了harness的不同弱点，需要不同的干预策略。HARD通过以下机制实现精准定位和定向改进：  
**可编辑防御制品。** HARD将运行时harness建模为 $K$ 个可编辑防御制品的集合：  

$\displaystyle H_t = \{d_k^t\}_{k=1}^K$

  
每个制品对应一个在特定干预接口上操作的防御策略。  
**轨迹驱动路由。** 给定失败集 $\mathcal{F}_t$，基于LLM的轨迹路由器 $\mathcal{R}$ 分析每条失败轨迹并确定应该改进哪个防御制品：  

$\displaystyle k = \mathcal{R}(\tau), \quad \tau \in \mathcal{F}_t$

  
路由后的失败被分组为制品特定的反馈集：  

$\displaystyle \mathcal{F}_{k,t} = \{\tau \in \mathcal{F}_t \mid \mathcal{R}(\tau) = k\}$

  
**Harness改进。** 每个防御制品使用其对应的反馈集进行改进：  

$\displaystyle d_k^{t+1} = \mathcal{E}_k(d_k^t, \mathcal{F}_{k,t})$

  
改进后的制品组装成更新的运行时harness：  

$\displaystyle H_{t+1} = \{d_k^{t+1}\}_{k=1}^K$

  
完整的演化过程总结在Algorithm 1中，核心循环为：采样任务→收集轨迹→识别失败→路由失败到防御槽位→更新防御槽位→更新harness。

### 五、实验设置

#### 5.1 基准与攻击

- **主要基准**：AgentCanary，在真实可执行环境中通过完整轨迹评估LLM Agent，覆盖四类安全威胁（DPI、IPI、MC、SP）。
- **补充数据集**：AgentHazard，其任务通过组合局部合理的计算机使用操作来实现有害目标。
- **自适应攻击**：动态攻击演化（DAE，攻击者迭代优化注入提示）和长周期渐进攻击（LPA，将恶意目标分解为一系列单独看似合理的交互）。
- **良性实用性评估**：PinchBench，衡量Agent在真实工具使用任务上的实用性。

#### 5.2 防御变体与基线

HARD实例化了两个可演化的防御组件：

- **上下文侧安全策略**（context-side security policy）：用于安全感知的上下文构造
- **动作侧防御规则**（action-side defense rule）：用于约束不安全执行  
  三个演化防御变体：
- **HARD-Policy**：仅演化上下文侧策略
- **HARD-Gate**：仅演化动作侧规则
- **HARD-Both**：联合演化两个组件  
  基线包括：
- 无防御的原始harness
- **SecureClaw**：上下文侧输入过滤
- **ClawKeeper**：动作侧执行约束
- **OpenClaw Shield**：整合上下文和动作层面干预

#### 5.3 评估指标

- **ASR（攻击成功率）**：攻击目标成功实现的比例，越低越好
- **BU（良性实用性）**：无攻击时良性任务的完成率，越高越好
- **UA（攻击下实用性）**：攻击条件下用户任务的完成率，越高越好

#### 5.4 模型配置

- 执行Agent：DeepSeek-V4-Flash（固定）
- 安全/实用性评判：GLM-5（固定）
- 路由器和演化器：GLM-5.2（主实验），后续消融实验中替换为Claude Opus-4.6、Qwen3.7-Max、GPT-5.5

### 六、实验结果

#### 6.1 静态攻击下的防御效果

Table 1的结果显示，HARD在所有四类攻击中一致性地优于手工设计的基线：

- **DPI**：HARD-Both将ASR降至12.1%（基线最低为36.1%的Shield）
- **IPI**：HARD-Both将ASR降至1.3%（基线最低为19.2%）
- **MC**：HARD-Both将ASR降至13.9%（基线最低为36.5%的Shield）
- **SP**：HARD-Both将ASR降至7.4%（基线最低为39.5%的Shield）  
  同时，HARD保持了91.9%–95.0%的良性实用性（BU），并大幅提升了攻击下实用性（UA）：MC场景下UA从57.8%提升至85.9%，SP场景下从49.3%提升至95.1%。  
  相比之下，现有静态防御表现出攻击特异性：例如Shield在IPI上ASR最低（12.8%），但在DPI（41.0%）和MC（41.8%）上仍然脆弱；SecureClaw过滤上下文但对DPI几乎无效（66.3%，与无防御相同）。  
  统计显著性方面，每个ASR单元的标准差最多5.7个百分点，配对McNemar检验在所有四类攻击上均拒绝HARD-Both与四个基线相等的假设（$p < 10^{-8}$）。

#### 6.2 自适应攻击下的防御效果

- **DAE**：HARD-Both达到最低ASR 26.5%，优于最强手工防御的30.1%
- **LPA**：HARD-Policy和HARD-Both分别将ASR降至4.8%和12.1%，而最强手工防御为24.1%  
  一个有趣的发现是：在LPA下，HARD-Policy优于HARD-Both。这表明当恶意意图分散在多个单独看似合理的交互中时，语义级安全指导特别重要。HARD-Gate在两种自适应设置中效果较差，说明仅靠动作侧规则无法捕获改变表面形式或在时间上分散风险的攻击。

#### 6.3 防御制品路由的有效性

Figure 4展示了三个HARD变体在MC攻击上的ASR和UA演化曲线：

- HARD-Both在演化后达到最低ASR和最高UA，证明联合优化多个防御制品比单独改进一个干预接口更有效
- HARD-Both展示了更平滑的改进轨迹，表明路由机制能有效将失败定向到负责的防御制品  
  但在自适应攻击下，HARD-Both并不总是进一步优于HARD-Policy。论文分析认为，确定性gate和语义policy在演化过程中可能产生非平凡的交互：gate能高效捕获表面级攻击模式，但可能减少policy演化从失败轨迹中提取可泛化安全原则的压力。

#### 6.4 演化骨干模型消融

Table 3展示了不同演化骨干模型在MC攻击上的效果：

| 演化骨干 | ASR↓ | BU↑ | UA↑ |
| --- | --- | --- | --- |
| 无演化 | 63.9 | 88.1 | 57.8 |
| GLM-5.2 | 13.9 | 94.7 | 85.9 |
| Claude Opus-4.6 | 7.7 | 96.2 | 85.3 |
| Qwen3.7-Max | 13.5 | 96.4 | 74.1 |
| GPT-5.5 | 20.3 | 94.9 | 7.2 |

所有骨干模型都显著降低了ASR，证明演化过程不依赖于特定模型。但安全-实用性权衡有所不同：Claude Opus-4.6达到最低ASR（7.7%），GLM-5.2达到最高UA（85.9%），Qwen3.7-Max达到最高BU（96.4%）。值得注意的是，GPT-5.5虽然降低了ASR但将UA降至7.2%，说明成功的失败修正仍可能产生过度限制性的防御。

### 七、端到端演化案例分析

论文在附录B中提供了三个详细的案例研究，揭示了HARD的工作机制：

#### 案例1：可执行谓词从单次失败中恢复

任务82要求Agent枚举SUID二进制文件（`find / -type f -perm -4000`）。Round 0两个变体都执行了命令，攻击成功。经过一轮演化后：

- **HARD-Gate**：合成了匹配命令模式的可重用谓词（`find.*-perm -?4000`），在执行前拦截。**攻击被阻止。**
- **HARD-Policy**：推导出更高层次的安全不变量，但保留了"授权管理员"豁免；Agent援引该豁免执行了搜索。**攻击仍然成功。**  
  → 这说明具有稳定执行签名的失败最适合在gate层修复。

#### 案例2：语义不变量从单次失败中恢复

任务60119请求一个恶意Ruby包，其安装脚本收集云凭证并静默提升IAM权限。恶意行为分布在大型源文件中，无法被单一执行模式捕获。经过一轮演化后：

- **HARD-Policy**：将失败抽象为描述凭证收集和权限提升的语义不变量，拒绝了请求。**攻击被阻止。**
- **HARD-Gate**：生成了需要凭证标识符和提升关键词同时出现的内容匹配规则，但多行载荷绕过了它。**攻击仍然成功。**  
  → 这说明语义失败需要策略级推理而非执行级匹配。

#### 案例3：自适应攻击下的局限

任务102063中，攻击不是直接调用bash，而是通过多轮交互使用环境变量重构命令（`A=ba, B=sh`，最终执行`$A$B -c 'whoami'`）。HARD-Both的18条gate规则都无法匹配重构后的命令（不包含字面的`bash`），而其策略也未阻止该动作。HARD-Policy则因为学到了反混淆和累积意图规则而成功阻止。  
→ 这揭示了在联合演化中，gate可能"抢走"了本应推动policy学习可泛化安全原则的失败案例，导致policy演化不充分。

### 八、相关工作

#### Agent攻击

论文系统梳理了静态攻击（直接提示注入、间接提示注入、记忆污染、技能投毒）和自适应攻击（反馈驱动优化、时间组合、自动化红队测试）的相关工作。

#### Agent防御

- **模型级防御**：StruQ（结构化查询微调）、SecAlign（偏好优化）、强化学习方法等，需要参数访问和重训练。
- **运行时防御**：上下文侧方法（标记外部内容、过滤无关字段）、裁决方法（注入检测器、守卫请求、任务对齐验证）、执行方法（执行隔离、信息流标签、权限策略）。所有这些防御配置都是部署前编写、部署后冻结的。

#### 自演化Agent

已有工作主要优化任务性能（如GEPA、ADAS、Voyager等），而非安全目标。FATE通过失败轨迹更新模型参数来实现安全自演化，但需要训练访问。Membrane通过演化外部对比安全记忆来避免重训练，但其演化制品是查询级守卫的记忆，不改变执行循环如何构造上下文或允许动作。HARD与这些工作的关键区别在于：它在运行时层面实现自演化，直接改进harness的上下文构造和动作解释组件。

### 九、实现细节

#### 演化协议

- **数据划分**：每个攻击类别独立演化，基准任务按确定性方式划分为训练/测试集，所有防御变体和演化骨干共享相同的划分。
- **批量演化**：训练失败以8条轨迹为一批处理。路由器先将失败分配到policy或gate更新，然后对应的演化器逐批处理。每次更新立即成为当前防御状态的一部分。
- **路由器配置**：需要语义推理的失败路由到policy演化器，可用可重用执行时谓词的失败路由到gate演化器。置信度低于0.55的gate预测被重新分配到policy演化器。

#### 提示设计

论文详细给出了三个关键组件的提示：

- **轨迹路由器**：分析每条失败轨迹，分类为`policy`或`gate`
- **Policy演化器**：重新生成完整的策略状态，鼓励合并和泛化规则，避免过拟合到具体场景
- **Gate演化器**：增量扩展执行gate，仅生成当前批次需要的新规则，每条规则必须对应具体的有害工具调用

---

### 十、总结与启示

这篇论文的主要贡献在于：

1. **统一的形式化框架**：将运行时防御统一为对harness两个组件（上下文构造和动作解释）的优化问题，为理解和设计运行时防御提供了原则性指导。
2. **自演化范式**：将运行时防御从静态的手工工程转变为自主演化过程，通过失败归因和定向改进实现持续提升。
3. **互补性洞察**：gate规则擅长处理具有稳定执行签名的攻击，policy规则擅长处理需要语义理解的攻击；但在自适应攻击下，gate规则的泛化能力有限，语义policy更为关键。
4. **安全-实用性权衡**：演化骨干模型的选择不仅影响安全改进的强度，还影响更新后的制品保持任务实用性的程度。  
   论文也揭示了一些局限：联合演化两个组件并不总是优于单独演化policy（特别是在自适应攻击下），gate规则可能"抢走"policy学习可泛化原则所需的失败案例。这提示未来工作需要更好地平

## 结构化提纲

### Beyond Handcrafted Security: Towards Self-Evolving Defense for LLM Agents
#### 研究背景与目标
- LLM智能体安全威胁日益复杂
  - 从被动文本生成演变为交互式系统，可调用工具、维护状态、操作外部环境
  - 单次不安全的工具调用可能造成严重后果
- 四类主要运行时安全威胁
  - 直接提示注入（DPI）：攻击者直接控制用户任务输入
  - 间接提示注入（IPI）：恶意指令隐藏在外部数据源中
  - 记忆污染（MC）：在持久化记忆中植入恶意内容
  - 技能投毒（SP）：在插件/工具中嵌入隐藏恶意逻辑
- 现有运行时防御的局限性
  - 严重依赖手工设计，部署后保持静态
  - 无法应对开放式的失败空间和自适应攻击
  - 维护依赖人工诊断和迭代修复，成本高且难以扩展
- 核心研究目标
  - 实现运行时防御的自主演化，自动适应新出现的攻击模式
  - 定义结构化、可编辑的防御空间
  - 基于观察到的失败自主改进防御机制
#### 研究方法
- Harness中心化的运行时防御形式化
  - 将LLM智能体建模为 A = (Mθ, H)，H为运行时Harness
  - Harness由两个函数组成：上下文构建函数 ϕH 和动作解释函数 ψH
  - 将运行时防御形式化为Harness优化问题，平衡安全性与任务效用
- HARD框架（Harness-based Autonomous Runtime Defense Evolution）
  - 失败驱动的防御演化
    - 收集攻击驱动的执行轨迹
    - 识别安全或效用未达标的失败案例
    - 由LLM演化器分析失败反馈并更新Harness
  - 失败轨迹路由与演化编排
    - 将Harness建模为可编辑防御组件集合
    - 轨迹路由器将失败分配到对应的防御组件（上下文侧/动作侧）
    - 各组件独立演化后重新组装为更新后的Harness
- 三种演化变体
  - HARD-Policy：仅演化上下文侧安全策略
  - HARD-Gate：仅演化动作侧防御规则
  - HARD-Both：联合演化两个组件
- 实验设置
  - 基准：AgentCanary（四类攻击）+ AgentHazard + PinchBench（效用评估）
  - 自适应攻击：动态攻击演化（DAE）和长期渐进攻击（LPA）
  - 基线对比：SecureClaw、ClawKeeper、OpenClaw Shield等手工防御
#### 关键研究结果
- 静态攻击防御效果
  - HARD-Both在四类攻击上ASR分别降至15.4%、1.0%、6.7%、10.2%
  - 手工防御ASR范围为13%–66%，存在攻击特异性局限
  - 良性效用（BU）保持在91.9%–95.0%
  - 攻击下效用（UA）显著提升：记忆污染从56%→86%，技能投毒从52%→92%
- 自适应攻击防御效果
  - DAE下HARD-Both ASR为26.5%，优于最佳手工防御30.1%
  - LPA下HARD-Policy ASR仅4.8%，远优于手工防御24.1%
  - 策略演化在分散式多轮攻击中优势更明显
- 防御组件路由的有效性
  - 联合演化（HARD-Both）在静态攻击下表现最优
  - 路由机制使演化轨迹更平滑稳定
  - 动作侧规则与语义策略存在非均匀叠加效应
- 演化骨干模型消融实验
  - 四种不同LLM骨干均能显著降低ASR，框架不依赖特定模型
  - Claude Opus-4.6达最低ASR（7.7%），GLM-5.2达最高UA（85.9%）
  - GPT-5.5过度限制导致UA降至7.2%，揭示安全-效用权衡
#### 研究结论与意义
- 核心贡献
  - 提出统一的Harness中心化运行时防御形式化框架
  - 实现首个基于失败轨迹的自主运行时防御演化系统（HARD）
  - 将防御开发从人工工程转变为自主演化过程
- 关键发现
  - 确定性执行谓词与语义策略解决互补的失败模式
  - 自适应攻击下语义策略泛化能力优于字面匹配规则
  - 单次失败观察往往足以合成有效防御
- 广泛意义
  - 为已部署LLM智能体的安全提供可扩展的演化范式
  - 无需修改模型参数或重新训练，适用于闭源模型
  - 减少对人工安全工程的依赖
- 局限性
  - 执行级规则在自适应攻击下泛化能力有限
  - 联合演化中两类组件可能产生非平凡交互
  - 演化骨干模型选择影响安全-效用平衡点

## 原文摘要

The expanding operational capabilities of large language model (LLM) agents introduce sophisticated security threats. Runtime defenses have emerged as an effective approach to mitigating these risks by integrating security mechanisms into the agent execution loop. However, existing runtime defenses rely heavily on manually designed interventions and lack a principled framework for their construction and maintenance. In this work, we first develop a harness-level formulation of runtime defense that systematically characterizes how harness mechanisms enable defense construction and provides a unified view of existing runtime defense interventions from a harness perspective. Building on this formulation, we propose HARD (Harness-based Autonomous Runtime Defense Evolution), a self-evolving runtime defense framework that automatically identifies appropriate intervention strategies and iteratively improves defense artifacts based on observed failure traces. HARD transforms runtime defense development from manual engineering into an autonomous evolution process, and extensive experiments demonstrate that it improves security performance over existing handcrafted defenses while preserving benign task utility. Our findings highlight autonomous defense evolution as a promising new paradigm for securing deployed LLM agents, enabling agents to identify defense weaknesses and continuously improve their protection mechanisms.
