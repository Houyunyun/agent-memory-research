# Infini Memory: Maintainable Topic Documents for Long-Term LLM Agent Memory

Ji, Suozhao, Wu, Baodong, Wang, Zehao, Xia, Lei, Li, Qingping, Wang, Ruisong, Ding, Wenbo, Zhu, Zhenhua, Li, Boxun, Dai, Guohao, Wang, Yu · 2026

## 核心机制

可维护主题文档、缓冲后整合和工具式迭代读取

## 适用范围与局限

主要以 MemoryAgentBench 评测，不能直接推断真实部署全覆盖

## 详细解读

### 论文核心总结

这篇论文提出了**Infini Memory**，一种面向长期LLM Agent的可维护持久记忆架构。其核心思想是将Agent的外部记忆组织为**按主题结构化的文本文档（topic documents）**，而非传统的孤立记录、摘要或向量索引片段。每个主题文档作为一个语义单元，聚合相关证据、保留元数据（时间戳、来源等），并支持事实的修订更新。在写入端，新观察先暂存到缓冲区，定期整合（consolidation）到主题文档库中；在读取端，采用一种**智能体式检索（agentic retrieval）**策略，让LLM通过迭代工具调用来多步搜索、检查和扩展证据，而非一次性检索。在MemoryAgentBench基准上，该系统取得了64.7%的总体得分，消融实验表明主题结构化维护和迭代证据检索分别改善了长期记忆使用的不同方面。

### 一、研究动机与问题定义

#### 1.1 长期Agent记忆的需求

LLM Agent越来越多地需要跨多个会话（session）长期运行。然而LLM的上下文窗口只限定了单次前向传播能关注的输入量。即使增加上下文长度，也无法自动解决三个问题：**哪些信息应该被保留**、**过时信息如何修订**、以及**相关证据如何组织以供未来使用**。  
因此，近年来的Agent系统引入了**持久记忆（persistent memory）**机制——一种外部的、可编辑的记忆状态，能跨交互会话存活，并在推理时被Agent写入、更新和查询。

#### 1.2 现有记忆系统的四个典型失败模式

论文在Figure 1中总结了现有记忆系统的四个反复出现的问题：

1. **记忆碎片化（Memory Fragmentation）**：当记忆以独立的可检索条目存储时，关于同一用户、任务或事件的证据会分散在许多小记录中，难以聚合。
2. **记忆冲突（Memory Conflict）**：当新观察与旧观察矛盾时，追加式存储会让新旧版本同时存在，检索时可能返回过时信息。
3. **长历史压缩损失（Compression Loss）**：将长历史压缩为摘要时，时间顺序和来源线索可能被削弱或丢失。
4. **检索不足以支撑推理（Insufficient Retrieval）**：基于向量相似度、关键词匹配或固定top-$k$的标准检索方法，可能返回孤立片段，缺乏足够的上下文来支持时间推理或矛盾解决。

#### 1.3 将持久记忆视为生命周期维护问题

基于以上观察，论文认为长期Agent的记忆模块应支持三个耦合操作：

- **写入（Write）**：将交互中的持久信息写入记忆状态。
- **维护（Maintain）**：对记忆状态进行分组、矛盾调和、保留时间和来源线索。
- **读取（Read）**：检索时提供足够的局部上下文，而非孤立片段。

### 二、相关工作

#### 2.1 持久记忆的表示与维护

论文梳理了几类已有工作：

- **上下文扩展类**：如MemGPT（虚拟上下文管理，在有限上下文和外部存储之间移动信息）、MemoryBank（基于艾宾浩斯遗忘曲线更新记忆）、Mem0（动态提取和整合对话信息，支持图结构变体）。这些系统通常以紧凑条目、摘要或索引片段存储记忆，后续修订和证据重建困难。
- **结构化记忆组织类**：如HippoRAG-v2（非参数记忆结构支持事实、联想和推理检索）、REMem（混合图表示情景记忆）、A-MEM（受Zettelkasten方法启发的原子笔记系统）。这些方法改善了记忆组织，但通常依赖原子笔记、嵌入或图结构。
- **LightMem**：将记忆处理分为感知过滤、主题感知短期整合和离线长期更新三个阶段。Infini Memory与之共享减少在线维护开销的动机，但更强调纯文本主题文档和显式整合操作。

#### 2.2 检索与评估

标准检索管道（向量相似度、关键词匹配、固定top-$k$）可能返回孤立片段。近期系统如REMem使用智能体式检索器迭代检索和推理，A-MEM在记忆构建时引入智能体能力。Infini Memory将智能体能力扩展到**读取路径**：LLM可以迭代选择记忆工具、检查中间结果、扩展局部上下文并组装证据。  
在评估方面，论文选择**MemoryAgentBench**作为主要评估基准，它通过增量多轮交互评估记忆Agent的四个核心能力：准确检索（AR）、测试时学习（TTL）、长程理解（LRU）和选择性遗忘（SF）。

### 三、Infini Memory的设计

#### 3.1 设计概览

Infini Memory将持久记忆表示为一个**主题文档库（library of topic documents）**。这里的"主题"（topic）指的是一个**维护范围（maintenance scope）**，将后续操作（路由、拆分、合并）中一起处理的条目分组在一起。这个范围由记忆在未来交互中的使用方式来定义。例如，关于一个稳定用户偏好或一个正在进行的项目的条目可能形成一个主题，因为它们为同一类未来问题和更新提供上下文。  
这种设计避免了两个不理想的极端：

1. 如果记忆存储为孤立记录，相关证据可能被分离，检索返回缺乏上下文的片段；
2. 如果所有记忆存储在单一时间序列日志中，后续操作可能需要扫描或重写无关历史。  
   整个记忆管道围绕四个环节组织：**表示（representation）**、**写入（writing）**、**整合（consolidation）**和**检索（retrieval）**。

#### 3.2 主题文档的表示

每个主题文档（Figure 2）包含两部分：  
**元数据头（Metadata Header）**：包括 `{id, summary, token_count, created_time, update_log, aux}`。  
**层次化正文（Hierarchical Body）**：使用主题和子主题标题组织无序列表形式的记忆条目。每个条目前缀一个可解析的签名：

```
<seq=..., time=..., source=...>
```

**条目级元数据（Entry-level Metadata）**：每个记忆条目至少携带一个序列号 $seq$（随每次写入单调递增）。当交互内容中有时间信息时记录 $time$ 字段；当信息从模型响应中提取时可附加 `source=AI` 标签。元数据签名还可以扩展领域特定字段，如实体类型、命名空间、机器标识符等。  
这种存储格式有三个实际好处：

1. 文档摘要和正文可以在维护时一起刷新，保持检索元数据与底层证据对齐；
2. 时间和来源线索随每个条目移动，即使内容被重写、拆分或合并；
3. 每个条目携带的元数据使后续修订显式化——当新证据更新早期内容时，$seq$ 和 $time$ 提供排序线索。

#### 3.3 缓冲写入与整合

写入和整合管道（Figure 3，完整过程见Algorithm 1）的设计围绕**记忆提取频率与记忆维护范围之间的不匹配**。记忆提取可能在每次交互后发生，但整合不应该如此频繁。如果每提取一个条目就更新主题库，需要反复进行主题路由、矛盾检查和文档重写，而且在相关证据积累足够之前可能引入不稳定的编辑。  
因此，Infini Memory引入了一个名为**CURRENT**的缓冲区。

##### CURRENT缓冲区

CURRENT以追加形式收集提取的记忆。追加到缓冲区不需要扫描或重写现有主题文档。更重要的是，缓冲区保留了近期交互的**短程连贯性**——几个相邻轮次通常描述同一任务、纠正同一事实或细化同一偏好。在整合之前将它们保持在一起，允许系统在进入主题库之前解决局部冗余和矛盾。

##### 缓冲区刷新条件

缓冲区在达到token阈值或活跃时间窗口时被刷新：  

$\displaystyle \text{flush}(C) = |C| \geq \tau_{\text{tok}} \lor \Delta t(C) \geq \tau_{\text{time}}$

  
其中 $C$ 表示当前缓冲区，$\tau_{\text{tok}}$ 是token阈值，$\tau_{\text{time}}$ 是时间阈值。

##### 整合流程

1. **重写（Rewrite）**：当缓冲区被刷新时，系统将CURRENT重写为REWRITE_CURRENT。这个中间草稿不是持久记忆存储，而是近期缓冲区的规范化视图。重写步骤将局部相关条目分组、移除冗余语句、保留有用元数据、标记对早期事实的可能更新。
2. **路由到主题库（Route to Topic Library）**：对于REWRITE_CURRENT中的每个块，规划器决定它应该更新现有主题文档还是创建新文档。如果扩展现有主题，则插入相关文档区域；如果更改早期事实，规划器记录更新关系并重写受影响的局部上下文；如果不适合任何现有维护范围，则创建新主题文档。
3. **清空缓冲区**：更新应用后，CURRENT被清空。但近期缓冲区内容在整合前仍可被检索模块使用，避免提取和可检索性之间的间隙。
4. **定期拆分与合并（Split & Merge）**：主题库通过拆分和合并操作定期更新。过大的文档被拆分以减少过于宽泛的局部上下文，碎片化的文档在描述相同维护范围时被合并。每次结构更新后，摘要和元数据被刷新。

#### 3.4 基于主题文档的智能体式检索

检索模块负责将主题库转化为用于答案生成的证据。Infini Memory支持两种检索变体：

##### 混合读取器（Infini Memory-H）

结合LLM基于摘要的文档选择与BM25分区检索（Figure 4）：

1. LLM根据文档摘要选择候选文档；
2. BM25对未选中的文档进行词汇匹配补充相关分区；
3. 将选中文档和相关分区交给LLM生成答案。

##### 智能体式读取器（Infini Memory-A）

LLM控制一个多步搜索过程（Figure 5）：

1. 系统暴露文档目录（文档ID + 摘要）和一组记忆工具；
2. 默认工具包括：全局词汇搜索（grep）、文档内模式搜索（grep_doc）、目录检查（list_docs）、行范围读取（read_lines）等；
3. Agent在工具调用和证据检查之间交替：早期步骤通常识别候选文档或标题，后期步骤读取局部区域并检查证据是否支持查询；
4. 循环在以下条件之一满足时停止：Agent返回停止决定、达到最大迭代次数、达到证据预算、或未能获得新的有用证据；
5. 最终证据集可能包含文档级选择、标题级块或扩展的行范围。片段级结果尽可能扩展到最近的连贯标题块；
6. 最终上下文还包括CURRENT中的近期条目；
7. 如果Agent未返回证据或证据不足，系统运行保守的词汇回退（BM25 fallback）。  
   完整检索循环见Algorithm 3。

#### 3.5 部署与可扩展性

Infini Memory使用结构化文本作为默认记忆载体。这种选择使默认后端保持简单——系统可以使用普通文档存储、词汇索引和确定性文件检查工具运行，不需要配置向量数据库、图数据库或外部记忆服务。  
这种设计应被理解为**后端轻量（backend-light）**而非无计算开销。智能体式检索可能比单步检索使用更多工具调用或LLM token，定期整合也引入维护成本。其好处是默认记忆状态保持可读、可编辑和可移植，同时可以在需要时添加更专业的检索后端。  
元数据区域可以存储命名空间、实体模式、访问规则或保留策略。额外工具可以暴露向量搜索、图遍历、数据库查找或权限检查。

### 四、实验

#### 4.1 实验设置

**基准测试**：MemoryAgentBench，评估四种能力：

- **准确检索（AR）**：从长历史中进行事实回忆
- **测试时学习（TTL）**：上下文中的规则获取
- **长程理解（LRU）**：扩展叙事理解
- **选择性遗忘（SF）**：更新过时信息

**基础模型**：gpt-5-mini。评估使用gpt-5作为LLM-as-Judge。  
**基线方法**：RAPTOR、MemoRAG、HippoRAG-v2、Mem0、MemGPT、LightMem、REMem，共7个基线。所有基线使用相同的4096-token分块策略。  
**记忆和检索配置**：

- CURRENT缓冲区在达到5000 token或时间阈值时触发重写
- 超过5000 token的主题文档被拆分，低于1000 token的文档基于摘要相似度被合并
- 检索时LLM接收查询和id + summary目录，Agent可调用记忆工具最多7轮
- 如果智能体式检索证据不足，BM25检索器补充非重复候选

#### 4.2 主要基准结果

如Table 1所示，**Infini Memory-A取得了64.7%的最高总体得分**，比最强基线（HippoRAG-v2的45.5%）提高了19.2个百分点，在所有四个能力上均领先：

- AR（准确检索）：+12.5%
- TTL（测试时学习）：+4.4%
- LRU（长程理解）：+25.4%
- SF（选择性遗忘）：+26.5%  
  与混合变体Infini Memory-H（61.3%）相比，智能体式检索平均增加3.4个百分点，最大增益在选择性遗忘上（+7.0%），因为显式的时间和来源线索帮助读取器追踪修订后的事实。

**关于多跳选择性遗忘（FC-MH）的讨论**：FC-SH（单跳）和FC-MH（多跳）之间81.0%/35.0%的差距揭示了写入时整合的结构性局限。单跳遗忘在写入时就能解决：重写阶段在主题文档内应用新近性覆盖。但多跳遗忘无法这样解决，因为推理链通常跨越多个在不同时间更新的主题文档，没有单次重写能强制跨文档一致性。

#### 4.3 消融实验

##### 4.3.1 结构维护消融

固定读取路径为混合读取器（Infini Memory-H），禁用结构维护（无计划驱动的拆分/更新和小文档合并，保留追加写入和CURRENT重写）。LongMemEval (S⋆) 上的准确率从76.0%降至69.3%，下降6.7个百分点。  
按问题类型分析（Figure 6），下降集中在**知识更新**和**多会话**问题上——这两类问题依赖于从远距离轮次中提取并在读取时调和的证据。没有拆分和合并，相关事实留在最初追加的文档中，被取代的条目继续与替代条目共存。

##### 4.3.2 检索策略消融

在相同维护记忆上比较三种读取路径（Table 2，Figure 7）：

- **仅摘要选择（Summary-only）**：41.7%——文档摘要无法捕获精确值、时间戳和实体提及等细粒度事实
- **混合检索（Infini Memory-H）**：76.0%——添加BM25分区检索恢复了大部分差距
- **智能体式检索（Infini Memory-A）**：79.3%——通过发起后续搜索、检查局部上下文和组合互补证据跨度进一步提升

##### 4.3.3 拆分阈值敏感性

在LongMemEval (S⋆) 上扫描文档拆分阈值（Table 3，Figure 8）：

| 阈值 | 文档数 | 准确率 | 变化 |
| --- | --- | --- | --- |
| ≥1000 | 762 | 74.0% | -2.0 |
| ≥3000 | 319 | 74.3% | -1.7 |
| ≥5000（默认） | 322 | 76.0% | — |
| ≥7000 | 280 | 70.7% | -5.3 |
| ≥9000 | 255 | 69.7% | -6.3 |

准确率曲线是**不对称的**：降低阈值（过度拆分）的代价较小，因为分区保持主题聚类，混合读取器仍能通过摘要+BM25匹配到达相关证据；但提高阈值（文档过大）的代价较大，因为过大的文档开始混合不相关子主题，降低了整合时的主题路由和检索时的分区级检索质量。

##### 消融总结

消融实验将增益归因于两个互补来源：

- 固定混合读取器，移除结构维护损失6.7个百分点（76.0→69.3）
- 固定维护记忆，从Infini Memory-H升级到Infini Memory-A增加3.3个百分点（76.0→79.3）  
  结构维护在此设置中贡献大于检索升级，但两个组件都不单独充分。

### 五、技术细节补充

#### 算法流程

**Algorithm 1（记忆写入与整合）**：

1. 从交互 $z_t$ 中提取记忆 $M$
2. 将 $M$ 追加到CURRENT缓冲区 $C$
3. 如果 $C$ 的token数未超过阈值，直接返回
4. 否则重写CURRENT为规范化草稿 $R$
5. 获取文档库摘要 $S_D$，规划更新 $P$
6. 对每个更新执行文档重写，对每个新文档创建并加入库
7. 清空CURRENT，如果启用合并维护则执行小文档合并
8. 刷新库元数据

**Algorithm 2（拆分感知的更新规划）**：如果内容超过规划拆分阈值，先按标题拆分为块，然后对每个块分别规划更新。如果规划结果不是有效JSON，则递归回退拆分。  
**Algorithm 3（智能体式记忆检索）**：

1. 获取库摘要 $S$，初始化历史 $H$
2. 循环最多 $\text{cfg.agentic\_max\_iterations}$ 次：Agent执行一步，如果完成则物化选择并跳出，否则执行工具调用并将结果加入历史
3. 如果证据为空或不足，执行BM25回退
4. 将证据与CURRENT近期条目合并，LLM生成答案

#### Prompt设计

论文在附录中提供了5个核心Prompt模板：

- **Prompt A（记忆提取）**：从交互中提取持久、可复用的记忆候选
- **Prompt B（CURRENT重写）**：将追加式CURRENT文档重写为干净的主题结构化Markdown草稿
- **Prompt C（更新规划）**：决定哪些现有文档应被更新、哪些内容应成为新主题文档
- **Prompt D（文档重写）**：将新内容合并到现有文档中
- **Prompt E（智能体式检索）**：驱动迭代搜索行为  
  所有写入侧Prompt遵循四个不变量：忠实于源文本、保留条目级元数据、通过显式新近性规则解决重复和矛盾、仅返回机器可解析输出。

#### 设计选择的理由

论文在附录A.2中解释了为什么不采用以下替代方案：

- **纯向量记忆**：离散条目易于追加和索引，但检索质量与片段粒度紧密耦合，随着库增长top-$k$检索难以恢复完整证据集
- **纯知识图谱**：图谱擅长表示显式关系结构，但许多交互记忆不自然映射到图边，且增加建模和维护成本
- **缓冲区+整合的必要性**：缓冲区允许交互期间高频追加写入，整合摊销了组织、修订和重新分配记忆的成本，类似人类记笔记的方式

---

### 六、结论

Infini Memory的核心贡献在于：

1. 提出了基于文档的持久记忆架构，将记忆组织为主题文档并通过缓冲写入和定期整合维护，避免对向量或图数据库的强制依赖；
2. 提出了智能体式检索策略，LLM控制多步搜索过程，支持迭代证据检查、局部上下文扩展和面向答案的证据组装；
3. 实验结果表明，持久Agent记忆质量同时取决于**记忆如何被维护**和**证据如何被检索**，两者缺一不可。

## 原文摘要

Long-term LLM agents need persistent memory that can track changing facts and provide relevant evidence across sessions. Existing memory systems often store observations as isolated records, summaries, or indexed fragments, which makes evidence aggregation, fact revision, and memory maintenance difficult. We propose Infini Memory, a maintainable text-based persistent memory architecture that treats agent memory as topic-structured documents. Each topic document serves as a semantic unit for collecting related evidence, preserving metadata, and revising facts over time. New observations are first staged in a buffer and periodically consolidated into coherent textual contexts. At inference time, an agentic retrieval procedure lets the LLM read memory through iterative tool calls rather than a single retrieval step. On MemoryAgentBench, Infini Memory achieves 64.7% overall score. Ablations show that topic-structured maintenance and iterative evidence inspection improve complementary aspects of long-term memory use.
