聚焦 LLM 多智能体系统中的共享经验、角色适配与团队持续学习；不穷尽传统多智能体强化学习。

1. 三种不同的「多 Agent 记忆」

多 Agent 管理记忆、团队使用记忆、群体传播经验，是三个相关但不等价的设置。 MIRIX 用不同管理角色协调多种记忆，G-Memory 则直接保存团队协作经验，SkillClaw 关注跨用户技能更新。三者都出现多个 Agent 或使用者，但研究对象、通信边界和评测目标不同 （MIRIX；G-Memory；SkillClaw）。

设置 主要问题 代表工作 不应混淆的判断
多角色管理同一记忆系统 谁负责提取、更新、检索不同记忆 MIRIX 管理模块多，不等于研究了协作团队的经验学习
同一团队共享或分配记忆 哪些经验共享，谁使用，如何改善协作 INMS、G-Memory、LEGOMem、LatentMem、LLMA-Mem 共用一个向量库，不代表已经解决角色适配与冲突
跨团队或跨用户传播经验 局部经验如何转成群体可用技能 SkillClaw 多用户生态不等于同一任务中的并行协作

Generative Agents 中多个角色保有经历并进行社会互动，为个体记忆如何影响群体行为提供了早期例子。但社会模拟的可信行为，与团队任务成功率或共享记忆的一致性，是不同评测对象 （Generative Agents；G-Memory）。

2. 五条方法路线

2.1 INMS：让孤立经验进入共享对话池

INMS 将实时记忆过滤、存储和检索置于异步多 Agent 交互中，使 Agent 能利用彼此的历史经验，并根据交互历史调整检索中介。与 G-Memory 强调多层组织协作轨迹相比，INMS 更直接回答「孤立 Agent 怎样建立动态知识交换通路」（INMS；G-Memory）。

需要注意版本差异：该 arXiv 条目始于 2024 年，早期标题与框架叙述使用 MS，当前版本使用 INMS。本专题采用当前摘要，不把早期版本的实验或机制拼接到当前结论里。建立共享池也不自动解决权限隔离、并发冲突或错误信息的传播。

2.2 G-Memory：记住团队如何合作，而不只是最终答案

G-Memory 采用 insight、query、interaction 三层图，将高层通用经验与细粒度协作轨迹联系起来。面对新任务，系统双向遍历这些层次，为不同 Agent 提供相关经验；任务完成后，新的交互继续进入记忆层级 （G-Memory）。

与 INMS 的共享交互通路相比，这条路线的突出点是保留「任务—交互—归纳经验」之间的组织关系。它适合作为研究团队经验表示的起点，但图中的关联并不是因果证明，也不能自动确认历史策略仍适用于当前工具、成员与权限设置 （G-Memory；INMS）。

2.3 LEGOMem：调度者和执行者应该记住不同内容

LEGOMem 从历史执行轨迹构建模块化程序记忆，并在 orchestrator 与任务 Agent 之间分配。论文在 OfficeBench 中观察到，调度者记忆有助于任务分解与委派，细粒度执行者记忆有助于操作准确性。相较 G-Memory 重点回答「如何组织协作经验」，LEGOMem 更直接回答「经验放在哪里、由谁使用」（LEGOMem；G-Memory）。

这提供了一个很有用的实验分解：只给调度者记忆、只给执行者记忆、两者都有、两者都没有。不能只比较「有记忆的团队」与「没有记忆的团队」，否则无法判断收益来自更好的规划，还是更好的工具执行。

2.4 LatentMem：共享经验，不共享完全一样的上下文

LatentMem 针对两类问题：缺少角色定制导致的记忆同质化，以及过细记忆条目导致的信息过载。其经验库保存轨迹，memory composer 根据检索经验与 Agent 上下文生成紧凑潜在记忆，再通过 LMPO 学习更有用的表示 （LatentMem）。

与 LEGOMem 在程序记忆的粒度和位置上做分工不同，LatentMem 进一步学习角色条件化的记忆表示。因此它不是纯粹的检索组件替换：评价时需计入 composer 的训练和生成成本，并区分高效压缩、角色适配与更多训练这几种贡献 （LatentMem；LEGOMem）。

2.5 LLMA-Mem：增加人数，还是增加团队经验？

LLMA-Mem 将团队规模与跨任务经验积累放在同一成本约束下考察，并在 MultiAgentBench 的编码、研究和数据库环境中评测不同记忆拓扑。原文观察到非单调的规模收益：更多 Agent 不总是带来更好的长期表现，记忆支持得更好的小团队可能超过较大的团队 （LLMA-Mem）。

这一问题补足了 G-Memory、LEGOMem 的局部机制视角：记忆不只是某个固定团队的增强器，还可能改变「应当使用多大团队」的选择。但这不能推导出少 Agent 普遍更好；任务并行性、角色异质性、通信代价和总预算仍可能改变结论 （LLMA-Mem；G-Memory；LEGOMem）。

3. 放在同一框架中比较

方法 记忆的主要组织方式 主要干预 最应单独控制的因素
INMS 动态共享对话池 实时过滤、存储与交互式检索 共享信息量、更新频率、通信成本
G-Memory insight/query/interaction 层次图 跨任务经验与角色相关协作轨迹检索 层次结构、轨迹细节与普通检索的独立贡献
LEGOMem 调度者与执行者的模块化程序记忆 按角色分配不同粒度经验 规划收益与执行收益的分离
LatentMem 原始经验库＋学习型记忆合成器 角色条件化潜在记忆 训练成本、压缩预算与角色适配
LLMA-Mem 灵活团队记忆拓扑 联合研究规模与终身学习 总预算、团队人数、任务序列和拓扑

上述方法并不组成可以直接排序的排行榜。不同任务、骨干、团队结构与成本单位下的最大涨幅不能拼接；本专题因此保留机制和实验边界，而不罗列跨论文百分比。

4. MAS 特有的记忆问题

私有、角色与团队记忆的边界

一个 Coder 的失败轨迹可以帮助 Reviewer，也可能包含不应传播的用户数据。LEGOMem 与 LatentMem 说明角色相关信息选择的重要性，INMS 展示共享通路的价值，但共享资格与任务效用仍须分别判断 （LEGOMem；LatentMem；INMS）。

可将每段记忆沿三个问题分析：谁生成、谁可以读取、谁有权将其提升为团队规则。这里的「提升」是本文的研究分析，不是宣称这些论文都实现了相同权限模型。

协作经验不同于结果记忆

「任务成功」不能说明所有中间沟通都有效。团队可能经过重复劳动、错误交接或偶然补救才成功。G-Memory 保留协作轨迹，LEGOMem 区分规划与执行，为这种归因提供了表示基础，但表示关系本身不证明是哪次交互带来了收益 （G-Memory；LEGOMem）。

多源更新、冲突与可信度

不同 Agent 可能基于过时工具输出更新同一事实，也可能把另一个 Agent 的猜测当成独立证据。AuthMem-Bench 与 EAL-Bench 原本关注记忆整合中的来源和授权状态；将其问题迁移到团队场景时，需要额外测试角色、转述链和共同来源，不能简单把多个 Agent 的一致意见当成多份独立证据 （AuthMem-Bench；EAL-Bench）。

群体传播与统一撤销

SkillClaw 展示经验转成共享技能并同步传播的路线，Mind Viruses 展示某些内容可以在 Agent 交互网络传播，SkillJack 则讨论污染经验转成技能后在源记录删除后仍然生效。这三类工作提示：源记录、团队摘要与派生技能之间的依赖，可能成为撤销和回滚的关键 （SkillClaw；Mind Viruses；SkillJack）。

这些风险也不能被写成必然失控。Mind Viruses 在其所测设置中认为风险当前有限，并发现简短警示具有较强抑制效果。后续研究应同时测传播条件、攻击可达性、正常任务效用和缓解效果。

5. 如何设计可信的团队记忆实验

以下为综合建议，不是对现有方法已经具备的能力作背书。

  1. 先隔离团队收益与记忆收益。 至少比较单 Agent 无记忆、单 Agent 有记忆、团队无记忆、团队有记忆；在相同总调用/token/工具预算下执行。
  2. 分离放置位置。 比较私有记忆、全共享记忆、调度者记忆和角色定制记忆。可以借鉴 LEGOMem 的角色分解，避免把全部变化包装为单一 memory gain。
  3. 保存真实任务时间顺序。 当前任务评分后才能把反馈用于后续任务；相邻同源题目可能引入泄漏，需要任务族隔离。
  4. 测通信而不只测成功率。 报告消息、检索、写入、摘要、冲突解决和 composer 训练的成本；必要时记录等待时间与重复工具调用。
  5. 改变团队而不只改变任务。 测成员替换、角色调整、工具版本变化后的经验适用性，区分对固定团队的记忆和可迁移协作知识。
  6. 记录净收益与失效。 同时测跨任务成功、负迁移、错误复用、过时事实、来源混淆和撤销后残留，而不是只选择最后或最好的一轮。

6. 推荐阅读顺序

  1. G-Memory：先理解团队协作轨迹为何不能只按普通文本切块保存。
  2. LEGOMem：再看记忆的角色分配，形成清晰的消融实验思路。
  3. LLMA-Mem：把局部记忆设计放回团队规模、任务流和成本问题。
  4. INMS：补充动态共享通路与异步交互的设计视角。
  5. LatentMem：进一步了解可学习、角色条件化的紧凑记忆。
  6. MIRIX、SkillClaw、Mind Viruses：分别补充管理分工、群体技能传播和传播风险；注意它们与核心团队记忆问题的边界。

7. 可以继续收窄的研究问题

对当前文献积累，一个比较集中的切入点是：局部经验什么时候应该成为团队规则，以及团队变化或权限撤销后如何取消这条规则的影响？ 它连接了 G-Memory 的协作轨迹、LEGOMem 的角色分配，以及 SkillJack 和授权记忆研究中的派生影响问题 （G-Memory；LEGOMem；SkillJack；EAL-Bench）。

这只是值得进一步验证的问题，不是「无人做过」的查新结论。下一步需明确固定哪一种团队、哪一类共享规则、哪些可观测反馈，再检索近邻工作和做小规模对照。
